# Weak-model case modification record

> This article records how the same batch of cases went from raw AI output to correction. The raw output was generated by Qwen3-8B-Q4_K_M, a small model deployed locally; the agent pipeline's engineering constraints (document chunking, context compression, output validation) reduce problems but cannot fully compensate for limited model capability, so the result depends directly on the model used. The source material is the two Excel files in [raw/](../raw/); the system under test is foli-mall.

## Case 1: the create-return API

**Raw AI output**:

```yaml
POST /api/returns
body: {"order_id": "12345", "reason": "defective",
       "return_type": "refund", "evidence_images": ["img1.jpg"]}
expect: 200, assert $.data.order_id == "12345"
```

**Issues found against the foli-mall contract**:

1. `order_id=12345` does not exist in the database; the API returns `204001 order not found`;
2. Wrong request field names: the real fields are `orderId / returnReason / returnType`; `evidenceImages` is a comma-separated string, not an array;
3. `return_type` must be an integer (0 = refund only, 1 = return and refund), not the string `"refund"`;
4. The asserted field `$.data.order_id` does not exist (the return VO uses `id / orderId / returnNo`).

**After correction (data delegated to plugins)**:

```yaml
preprocessors:
  - name: return-fixture          # creates a COMPLETED order + return record, injects returnId
    config:
      return_status: 0            # PENDING_REVIEW
      return_type: 1
assert_dict:
  code: '100000'
assert_rules:
  - $.data.id is_not_null
  - $.data.orderId is_not_null
  - $.data.status == 0
```

**What the plugin did**: `return-fixture` creates the "completed order + return record" in a single SQL pass, turning what used to be 3–4 tables of manual setup into zero effort, and can clean up after the case finishes.

## Case 2: the full return business flow (standard return/refund flow)

**Raw AI output (5 steps)**: login `testuser/Test@123` → create a return (`orderId=12345`) → ship the item back (hard-coded URL `12345`) → query the detail.

**Issues found against the business rules**:

1. The account `testuser/Test@123` does not exist (the seed accounts are `buyer01/buyer123` etc.);
2. A newly created return is `PENDING_REVIEW(0)`, but `ship-back` requires `APPROVED(1)` — **the seller approval step is missing**, so the whole flow necessarily fails with `208002`;
3. The URL hard-codes `12345` instead of using `inherit` to pass the `returnId` from the previous step;
4. The flow only uses the buyer perspective; the seller/admin roles are missing.

**After correction (10 steps, full return state machine)**:

```text
Step_Login_Buyer   buyer01/buyer123
Step_CreateReturn  order-fixture creates COMPLETED order + POST /api/returns → assert status=0
Step_Login_Seller  seller01/seller123
Step_Approve       PUT /api/seller/returns/#{returnId}/approve
Step_ShipBack      PUT /api/returns/#{returnId}/ship-back (buyer01)
Step_Login_Seller  seller01
Step_Confirm       PUT /api/seller/returns/#{returnId}/confirm-receipt
Step_InspectPass   PUT /api/seller/returns/#{returnId}/inspect-pass
Step_Verify        GET /api/returns/#{returnId} → assert status=6 (refunded)
```

**What the plugin did**: `order-fixture` pushes the order straight to COMPLETED, skipping the four prerequisite steps (order → pay → ship → receive) so the case can focus on the return state machine itself. Human review adds business understanding, while plugins take care of data preparation.

## Case 3: the order-and-pay flow (happy path verification)

**Raw AI output**: login → view cart → create order → pay → cancel → receive (implicitly assuming "after order creation the status is pending payment").

**Issues found against the business rules**: foli-mall's `POST /api/orders` **deducts balance and sets the order to PAID(1) at creation time**; `pay` and `cancel` only accept `PENDING_PAY(0)`, so "pay/cancel after creation" always returns `204002`. The AI applied a generic e-commerce state machine without reading foli-mall's implementation.

**After correction**: "pay" becomes a negative assertion (`204002 invalid order status`); `cart-fixture` guarantees selected cart items; `balance-fixture` sets the balance to 0.01 to reproduce `205001 insufficient balance`, then restores it afterwards.

## Case count and execution results

Against all 91 single-API cases and 15 flow sheets in the two raw Excel files, `curated/` contains **74 cases (65 single-API + 9 business flows)**, all corrected to foli-mall's real contract and executed end to end: **71 passed, plus 3 foli-mall bug-evidence cases failing as expected** (see [foli-mall-bugs-found.md](./foli-mall-bugs-found.md)).

### Fixture plugins

The curated cases use six database fixture plugins (see [plugin-guide.md](./plugin-guide.md)); user-fixture and product-fixture cover the following prerequisite states:

- `user-fixture`: idempotent register (predelete + cleanup), disabled account (set_status=0 → 201003), and /me after user deletion (delete → 201004);
- `product-fixture`: insufficient-stock order (set_stock), deleting a cart item of an off-shelf product (set_status=4), and deleted-product listing (set_deleted); post cleanup restores original values to protect the shared seed products.

### Key correction notes

- Invalid-ID cases using 19 nines exceed the `Long` upper bound and cause HTTP 500; they were changed to well-formed 18-digit non-existent IDs;
- Fixed-ID cart inserts create multiple rows for the same product per user, breaking later `POST /api/cart` (`selectOne` returns too many rows); cart cases now use buyer02 to keep buyer01's order-creation cases clean;
- `GET /api/orders` sorts by create time descending and ties are unstable within the same second, so list cases no longer assert `records[0].status`; order status is covered by the detail case.
